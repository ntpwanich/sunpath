# เกณฑ์ตัดสินว่าอะไรควรเป็นตารางแยก และการไม่เก็บค่าที่คำนวณได้

การออกแบบ schema รอบแรกแกว่งไปมาระหว่างสองขั้ว — ขั้วหนึ่งแยกทุกแนวคิดเป็นตารางจนงานขายหนึ่งชิ้นเหลือแต่ foreign key ห้าตัวและอ่านแถวเดียวแล้วไม่รู้อะไรเลย อีกขั้วหนึ่งยุบทุกอย่างลง `Opportunity` จนกลายเป็นตารางสามสิบคอลัมน์ที่ต้องอ่านคู่กันทีละกลุ่มถึงจะเข้าใจ ปัญหาไม่ได้อยู่ที่ว่าขั้วไหนถูก แต่อยู่ที่ไม่มีเกณฑ์เขียนไว้ ทำให้ของที่หน้าตาเหมือนกันถูกตัดสินคนละแบบในการสนทนาเดียวกัน

**เกณฑ์ที่ใช้ตัดสิน เรียงตามลำดับ**

1. *มีหลักฐานว่าต้องใช้ไหม* — มีหน้าจอ กติกา หรือรายงานตัวไหนที่ต้องการข้อมูลนี้ ถ้าไม่มี ไม่ใส่ ไม่ว่าจะดูสมมาตรแค่ไหน
2. *ลูกมีได้ไม่จำกัดจำนวนไหม* — ความสัมพันธ์ 0..n ที่ไม่มีเพดานต้องเป็นตาราง ไม่ใช่ array และไม่ใช่คอลัมน์ที่ลงท้ายด้วยเลข
3. *วงจรชีวิตต่างจากแม่ไหม* — ลูกที่เกิด ตาย หรือถูกแช่แข็งคนละจังหวะกับแม่ ต้องแยก
4. *ต้องรู้ประวัติหรือรู้แค่ค่าปัจจุบัน* — ต้องรู้ประวัติคือตารางที่เขียนเพิ่มอย่างเดียว รู้แค่ค่าปัจจุบันคือคอลัมน์
5. *มี invariant ที่บังคับได้เฉพาะรูปแบบเดียวไหม* — unique constraint ที่ต้องการมีที่ยืนได้แบบเดียว ให้รูปแบบนั้นชนะ
6. *ค่านี้คำนวณจากของที่มีอยู่ได้ไหม* — ได้แล้วไม่เก็บ ไม่ว่าจะอยู่ในตารางแยกหรือไม่
7. *ถ้ายังก้ำกึ่ง* — แยกเป็นตาราง

ข้อ 7 ไม่มีคำตอบที่ถูกในทางเทคนิค เป็นการเลือกครั้งเดียวเพื่อให้ของที่ก้ำกึ่งทุกชิ้นถูกตัดสินเหมือนกัน ผลคือ `OpportunityQualification` `OpportunityWin` `OpportunityLoss` และ `QuotationRevisionDiscountApproval` เป็นตารางทั้งหมด ทั้งที่ทุกตัวเป็นความสัมพันธ์ 0..1 ที่ยุบเป็นฟิลด์ได้ เหตุผลที่เลือกแยกคือกลุ่มข้อมูลอ่านออกจากชื่อตาราง ไม่ต้องอ่านฟิลด์ที่ว่างได้ห้าตัวเรียงกันแล้วเดาว่าตัวไหนใช้ตอนไหน และได้ผลพลอยได้ว่าเหตุผลที่แพ้งานกลายเป็นคอลัมน์ที่ว่างไม่ได้ในทางฐานข้อมูล

**สิ่งที่ถูกปฏิเสธด้วยเกณฑ์ชุดนี้**

ตาราง `Site` แยกต่างหากสำหรับหลังคา — ตกข้อ 3 เพราะค่าไฟต่อเดือนและประเภทหลังคาที่เก็บไว้คือคำบอกเล่าของผู้สนใจ ณ วันที่ทักเข้ามา ไม่ใช่คุณสมบัติถาวรของอาคาร ถ้าใช้แถวเดิมซ้ำ การแก้ค่าไฟในงานชิ้นใหม่จะเปลี่ยนความหมายของงานที่ปิดไปแล้วย้อนหลัง

ตาราง lookup สำหรับอัตราค่าเดินทาง ราคาต่อกิโลวัตต์พีค เส้นตาย และโควตางานค้าง — ตกข้อ 1 เพราะไม่มีหน้าจอให้ใครแก้ค่าเหล่านี้ และถ้าย้ายเข้าฐานข้อมูล กติกาทางธุรกิจจะทดสอบไม่ได้โดยไม่มีฐานข้อมูล ซึ่งขัดกับเงื่อนไขของ [ADR 0001](./0001-nextjs-fullstack-with-isolated-domain-layer.md)

soft delete และตาราง audit กลาง — ตกข้อ 1 เพราะข้อมูลถูกสร้างใหม่ทุกคืนตาม [ADR 0002](./0002-vercel-neon-with-nightly-reseed.md) อยู่แล้ว และ `deletedAt IS NULL` ที่ต้องพกไปทุก query คือจุดที่ลืมแล้วข้อมูลรั่วโดยไม่มีใครรู้

**ค่าที่คำนวณได้จะไม่ถูกเก็บลงตาราง**

ขนาดระบบประเมิน มูลค่าคาด เส้นตายการตอบสนอง เวลาที่ติดต่อครั้งแรก เวลาที่เปลี่ยน Stage ล่าสุด และจำนวนวันที่งานค้างอยู่ ทั้งหมดคำนวณจากข้อมูลที่เก็บไว้แล้วด้วยฟังก์ชันบริสุทธิ์ที่มี unit test เหตุผลคือระบบนี้ตัดสินแทบทุกอย่างด้วยเวลาและด้วยตัวเลขที่ได้จากสูตรเดียวกัน ค่าที่เก็บซ้ำไว้จะเพี้ยนจากค่าจริงตั้งแต่ครั้งแรกที่มีทางเขียนสักทางลืมอัปเดต แล้ว dashboard จะแสดงตัวเลขผิดโดยไม่มีอะไรพัง ซึ่งเป็นความล้มเหลวที่เงียบกว่าการที่มันช้า ถ้าวันหนึ่งช้าจริง ทางแก้คือ materialized view หรือ read model แยกที่รู้ตัวว่าข้อมูลเก่า ไม่ใช่คอลัมน์ที่ไม่มีใครรู้ว่าอัปเดตครั้งสุดท้ายเมื่อไหร่

**คอลัมน์ `Opportunity.contactIdWhileOpen`**

กติกาจับข้อมูลซ้ำต้องการให้คนหนึ่งคนมีงานที่ยังไม่ปิดได้ทีละงานเดียว สิ่งที่ตรงกับความต้องการนี้ที่สุดคือ partial unique index บน `contactId` เฉพาะแถวที่ Stage ยังไม่ปิด แต่ Prisma ประกาศ partial index ใน schema ไม่ได้ และถ้าเขียนเพิ่มเองในไฟล์ migration คำสั่ง `prisma migrate dev` ครั้งถัดไปจะสร้าง migration ที่ลบ index นั้นทิ้งให้เงียบ ๆ เพราะมันไม่มีอยู่ใน schema กับดักนี้จะอยู่กับโปรเจกต์ไปตลอดทุกครั้งที่แก้ schema

จึงใช้คอลัมน์ที่มีค่าเท่ากับ `contactId` ตอนงานยังเปิดและเป็น NULL ตอนปิดแทน เพราะ Postgres ยอมให้ค่า NULL ซ้ำกันได้ใน unique index ราคาที่จ่ายคือคอลัมน์ซ้ำหนึ่งตัวที่ต้องเขียนให้ถูกในสองจังหวะเท่านั้น — ตอนเปิดงานและตอนปิดงาน ซึ่งทั้งคู่อยู่ในชั้น use-case เดียวกับที่เปลี่ยน Stage อยู่แล้ว ที่ยอมจ่ายเพราะกติกาข้อนี้ต้องพิสูจน์ได้ด้วยฐานข้อมูลจริง ไม่ใช่ด้วยการเช็คในโค้ดซึ่งผ่านทั้งคู่เมื่อสอง request เข้ามาพร้อมกัน
