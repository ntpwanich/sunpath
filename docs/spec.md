เอกสารนี้เป็นผลของการออกแบบร่วมกันก่อนเริ่มพัฒนา ใช้เป็นตัวตั้งต้นของ session ที่จะลงมือเขียนโค้ด

## 1. ลูกค้าสมมติ

**ไทยซัน โซลูชั่น** ผู้รับเหมาออกแบบและติดตั้งระบบโซลาร์รูฟท็อป สำนักงานอยู่กรุงเทพฯ รับงานในกรุงเทพฯ ปริมณฑล และจังหวัดใกล้เคียง

| | |
|---|---|
| พนักงานทั้งบริษัท | ราว 40 คน |
| ฝ่ายขายและสำรวจ | ผู้จัดการฝ่ายขาย 1 · เซลส์ 8 · ช่างสำรวจ 4 · ธุรการ 1 |
| Segment ที่ขาย | บ้านพักอาศัย (ดีลละ 150,000-400,000 บาท ปิดใน 2-6 สัปดาห์) และโรงงาน/อาคารพาณิชย์ (ดีลละ 1-10 ล้านบาท ปิดใน 2-6 เดือน) |
| ผู้สนใจเข้ามาจาก | LINE OA, โฆษณาบน Facebook, ฟอร์มบนเว็บไซต์, งานแฟร์, ลูกค้าแนะนำ |
| เครื่องมือปัจจุบัน | Excel คนละไฟล์ต่อเซลส์, กลุ่มไลน์หลายกลุ่ม, สมุดจดของช่างสำรวจ, ใบเสนอราคาทำใน Excel แล้วส่ง PDF ทางไลน์ |

ขอบเขตของระบบคือตั้งแต่มีผู้สนใจทักเข้ามา จนถึงปิดการขายและรับมัดจำ
งานขออนุญาตและขนานไฟกับการไฟฟ้า (45-90 วัน) และงานติดตั้ง อยู่นอกขอบเขต ระบบเพียงทำเครื่องหมายว่าส่งต่อให้ฝ่ายติดตั้งแล้ว

## 2. ตัวละคร

**คุณวิทย์ — ผู้จัดการฝ่ายขาย**
อยากรู้ทุกเช้าว่ามีงานไหนกำลังจะหลุด เซลส์คนไหนงานล้น และเดือนนี้มีมูลค่าค้างอยู่ในระบบเท่าไหร่ ทุกวันนี้ต้องไล่ถามทีละคนและรอไฟล์ Excel สองวันกว่าจะได้ภาพรวม

**คุณเมย์ — เซลส์บ้านพักอาศัย**
รับผู้สนใจวันละหลายราย ต้องจำว่าใครคุยถึงไหน ใครรอใบเสนอราคา ใครเงียบไปแล้วกี่วัน ทุกวันนี้ใช้ความจำกับโน้ตในมือถือ

**คุณต้น — ช่างสำรวจ**
วันหนึ่งวิ่ง 2-3 หลัง ถ่ายรูปหลังคาเก็บไว้ในมือถือ แล้วโทรบอกเซลส์ตอนเย็น ข้อมูลตกหล่นระหว่างทางบ่อย

**คุณอร — ธุรการ**
ดูแลรายชื่อผู้ใช้และความถูกต้องของข้อมูลในระบบ

## 3. ปัญหาที่ระบบนี้แก้

1. ผู้สนใจทักเข้ามาแล้วไม่มีใครรับผิดชอบชัดเจน หรือเซลส์สองคนโทรหาคนเดียวกัน
2. ไม่มีใครรู้ว่าผู้สนใจรายใหม่ถูกติดต่อกลับช้าไปแล้วกี่ชั่วโมง
3. ผลสำรวจหน้างานอยู่ในมือถือช่าง ไม่ได้อยู่กับงานขาย
4. ใบเสนอราคาที่แก้หลายรอบ ไม่มีใครรู้ว่าลดราคาไปแล้วเท่าไหร่
5. ผู้จัดการมองไม่เห็นภาพรวม ต้องรวบรวมด้วยมือทุกครั้งที่อยากรู้
6. ไม่มีใครรู้ว่างานที่เงียบไปนั้นเงียบมานานแค่ไหน

## 4. เส้นทางการขาย

```
ผู้สนใจใหม่ → ติดต่อแล้ว → ผ่านคัดกรอง → นัดสำรวจ → สำรวจแล้ว → เสนอราคา → ต่อรอง → ปิดการขาย
                                                                                    ↘ ไม่สำเร็จ
```

เหตุผลที่แยก "นัดสำรวจ" กับ "สำรวจแล้ว" ออกจากกัน เพราะช่างสำรวจเป็นทรัพยากรที่มีจำกัดที่สุดของธุรกิจนี้ และเป็นจุดที่งานค้างมากที่สุดจริง

การออกจาก Stage หนึ่งมีเงื่อนไข ไม่ใช่การเลื่อนอิสระ เช่น เข้าสู่ "เสนอราคา" ไม่ได้ถ้ายังไม่มี Survey Report และปิดการขายไม่ได้ถ้ายังไม่มี Quotation Revision ที่ออกไปแล้ว

## 5. บทบาทและสิทธิ์

| บทบาท | เห็นอะไร | ทำอะไรได้ |
|---|---|---|
| ผู้จัดการฝ่ายขาย | ทุก Opportunity ของทั้งบริษัท | จัดคิวช่างสำรวจ เปลี่ยนเจ้าของงาน ดู dashboard ทั้งทีม อนุมัติส่วนลดเกินเพดาน |
| เซลส์ | เฉพาะงานที่ตนเป็นเจ้าของ | เลื่อน Stage คัดกรอง บันทึก Activity ออก Quotation ปิดงาน |
| ช่างสำรวจ | เฉพาะงานสำรวจที่ถูกมอบหมายให้ตน | กรอก Survey Report แนบรูป ระบุว่าสำรวจแล้ว |
| ธุรการ | รายชื่อผู้ใช้ | เพิ่ม ลบ ปิดการใช้งานผู้ใช้ |

สิทธิ์ทำที่ระดับ role ตรง ๆ ไม่ทำระบบ permission ที่ตั้งค่าได้เอง

## 6. ข้อมูลหลัก

- **Opportunity** — งานขายหนึ่งชิ้น ระเบียนเดียวตลอดเส้นทาง ดู [ADR 0003](./adr/0003-single-opportunity-record-instead-of-lead-and-deal.md)
  ผู้สนใจ (ชื่อ เบอร์ ช่องทางที่มา) · ที่ตั้ง (จังหวัด เขต) · Segment · ค่าไฟต่อเดือน · ประเภทหลังคา · กรรมสิทธิ์ · เจ้าของงาน · Stage · มูลค่าคาด · ขนาดระบบประเมิน · ขนาดระบบที่ยืนยันแล้ว · เหตุผลที่ปิดไม่สำเร็จ
- **Customer** — เกิดเมื่อปิดการขายสำเร็จเท่านั้น
- **SurveyAssignment** — ช่างคนไหน วันไหน ช่วงเช้าหรือบ่าย
- **SurveyReport** — ขนาดที่ติดตั้งได้จริง สภาพหลังคา น้ำหนักต่อตารางเมตร เงาบัง ระยะตู้ไฟ รูปถ่าย ข้อสังเกตของช่าง
- **QuotationRevision** — เลขที่ เวอร์ชัน รายการอุปกรณ์ ราคา ส่วนลด ประมาณการประหยัดต่อเดือน ช่วงคืนทุน สถานะ (ร่าง / ออกแล้ว / ลูกค้ารับ / ลูกค้าปฏิเสธ) ฉบับที่ออกแล้วแก้ไม่ได้
- **Activity** — สิ่งที่เกิดขึ้นไปแล้ว (โทร ไลน์ นัดเจอ บันทึก)
- **FollowUpTask** — สิ่งที่ต้องทำและกำหนดเวลา ระบบสร้างเองเมื่อเปลี่ยน Stage
- **User** — ชื่อ บทบาท สถานะใช้งาน

## 7. กติกาที่ทำให้ระบบนี้ไม่ใช่แค่ตารางข้อมูล

1. **คัดกรองอัตโนมัติ** จากค่าไฟ จังหวัด ประเภทหลังคา และกรรมสิทธิ์ ระบบแนะนำ เซลส์ override ได้แต่ต้องระบุเหตุผล และเหตุผลนั้นถูกเก็บไว้ดูย้อนหลังได้
2. **ประเมินขนาดระบบและผลตอบแทน** จากค่าไฟต่อเดือน แล้วถูกแทนที่ด้วยตัวเลขจริงหลังสำรวจ
3. **แจกงานวนอัตโนมัติ** ตาม Segment ข้ามเซลส์ที่มีงานค้างเกินโควตา
4. **จับข้อมูลซ้ำด้วยเบอร์โทร** ผูกเป็นการติดต่อครั้งใหม่ของงานเดิม ไม่สร้างงานซ้ำ
5. **เส้นตายการตอบสนอง** คำนวณให้ทุกงานตาม Segment เลยกำหนดแล้วขึ้นธงบนหน้าจอผู้จัดการ
6. **เงื่อนไขการเลื่อน Stage** ตามข้อ 4
7. **ใบเสนอราคาที่ออกแล้วแก้ไม่ได้** การต่อรองสร้างเวอร์ชันใหม่ที่อ้างถึงฉบับเดิม
8. **กันคิวช่างชนกัน** และเตือนเมื่อช่างคนหนึ่งมีเกินสามงานในวันเดียว

รายละเอียดตัวเลขทั้งหมดอยู่ใน [business-rules-draft.md](./business-rules-draft.md)

## 8. เส้นทางการใช้งานหลัก

**เส้นทางที่ 1 — จากผู้สนใจถึงปิดการขาย (เส้นทางหลักที่ใช้สาธิต)**
ผู้สนใจกรอกฟอร์ม → ระบบสร้าง Opportunity แจกให้เซลส์ตาม Segment พร้อมเส้นตาย 2 ชั่วโมง → เซลส์โทรและบันทึก Activity → คัดกรอง ระบบแนะนำว่าผ่าน → ผู้จัดการจัดคิวให้ช่างวันพฤหัส → ช่างเปิดมือถือหน้างาน กรอกผลสำรวจและแนบรูป → เซลส์ออกใบเสนอราคาจากตัวเลขที่ช่างยืนยัน → ลูกค้าต่อราคา เซลส์ออกเวอร์ชันสอง → ปิดการขาย ระบบสร้าง Customer และทำเครื่องหมายส่งต่อฝ่ายติดตั้ง

**เส้นทางที่ 2 — เช้าวันจันทร์ของผู้จัดการ**
เปิด dashboard เห็นทันทีว่ามีสามงานเลยเส้นตายและใบเสนอราคาสองใบเงียบเกินเจ็ดวัน กดเข้าไปดู เปลี่ยนเจ้าของงานที่เซลส์คนหนึ่งรับไม่ไหว

**เส้นทางที่ 3 — วันทำงานของช่างสำรวจ**
เปิดมือถือเห็นสองงานของวันนี้พร้อมที่อยู่และเบอร์ลูกค้า ไปถึงหน้างาน กรอกฟอร์ม ถ่ายรูป กดส่ง เซลส์เห็นผลทันที

**เส้นทางที่ 4 — คัดกรองแล้วไม่ผ่าน**
ผู้สนใจค่าไฟเดือนละ 1,200 บาท อยู่หัวหิน ระบบแนะนำให้ตีตก เซลส์ปิดงานพร้อมเหตุผล งานไปอยู่ในรายงานว่าเสียเพราะอะไร

### ปฏิทินคิวสำรวจ (หน้า 7) — ขอบเขต
มุมมองรายสัปดาห์ แกนนอนเป็นวัน แกนตั้งเป็นช่างสี่คน ลากงานจากแถบรอจัดคิวลงช่องได้ ย้ายวันได้ กันเวลาชนกัน เตือนเมื่อเกินสามงานต่อวัน แต่ละช่องแสดงชื่อผู้สนใจและจังหวัดเพื่อไม่ให้ช่างถูกส่งข้ามเมืองในวันเดียวกัน
ไม่ทำ: มุมมองรายเดือน งานซ้ำเป็นรอบ การลากขยายช่วงเวลา และระบบวันลาของช่าง

### Dashboard (หน้า 6) — ลำดับความสำคัญ
แถวบนสุดคือความเสี่ยง ไม่ใช่ยอดขาย
1. งานที่เลยเส้นตายแล้ว
2. ผู้สนใจใหม่ที่ยังไม่มีใครติดต่อ
3. ใบเสนอราคาที่เงียบเกินเจ็ดวัน

ถัดลงมาคือ มูลค่าที่ค้างอยู่ในเส้นทางขายแยกตาม Stage · ปิดได้เดือนนี้เทียบเดือนก่อน · อัตราปิดรายเซลส์ · ภาระงานของช่างสำรวจสัปดาห์นี้ · เหตุผลที่แพ้งานที่พบบ่อยที่สุด

เหตุผลของลำดับนี้: ยอดขายดูใน Excel ก็ได้ แต่ "งานที่กำลังจะหลุดตอนนี้" คือสิ่งที่ Excel ทำไม่ได้

## 10. อยู่นอกขอบเขตโดยตั้งใจ

งานขออนุญาตและขนานไฟ · การบริหารโครงการติดตั้ง · การวางบิลและรับชำระเงิน · สัญญาและเอกสารกฎหมาย · สต็อกอุปกรณ์ · บริการหลังการขายและการรับประกัน · ระบบ permission ที่ตั้งค่าเองได้ · การรองรับหลายบริษัทในระบบเดียว · การเชื่อมต่อ LINE OA ของจริง · แอปมือถือที่ต้องติดตั้ง

การระบุสิ่งที่ไม่ทำและเหตุผล มีค่าต่อการเล่าเรื่องเท่ากับสิ่งที่ทำ

## 11. ข้อมูลตัวอย่าง

- Opportunity ราว 180 รายการ กระจายย้อนหลังเก้าเดือน ทุก Stage มีงานอยู่จริง
- Customer ที่ปิดได้ 60 ราย
- Activity ราว 900 รายการ
- เซลส์ 8 คนที่ผลงานต่างกันชัดเจน มีทั้งคนที่ปิดเก่งและคนที่งานค้างเยอะ
- ช่างสำรวจ 4 คน มีคิวเต็มสัปดาห์นี้
- มีงานที่เลยเส้นตายอยู่จริงในระบบ เพื่อให้ dashboard มีอะไรให้ดู
- ชื่อคน ชื่อโรงงาน ที่อยู่ เขต และจังหวัด ต้องเป็นของไทยจริงทั้งหมด ห้ามใช้ชื่อสมมติแบบสากล
- ค่าไฟ ขนาดระบบ และราคา ต้องสอดคล้องกันตามสูตรในกติกาทางธุรกิจ ไม่ใช่สุ่ม

ข้อมูลชุดนี้ถูกรีเซ็ตกลับสู่สถานะตั้งต้นทุกคืน ดู [ADR 0002](./adr/0002-vercel-neon-with-nightly-branch-reset.md)

## 12. กรณีศึกษาหน้าแรก

โครงของหน้า `/case-study` เรียงตามลำดับ: หัวเรื่องพร้อมปุ่มลองใช้ระบบ · ลูกค้าคือใคร · ปัญหาที่เล่าเป็นเหตุการณ์จริงไม่ใช่รายการหัวข้อ · ผังการทำงานก่อนและหลังวางคู่กัน · สี่สิ่งที่ระบบแก้ แต่ละข้อมีภาพประกอบหนึ่งภาพ · ภาพเดินตามเส้นทางขายทั้งเส้น · สิ่งที่ตั้งใจให้เกิดขึ้นพร้อมคำระบุชัดว่าเป็นกรณีศึกษาสมมติ · ภาพรวมทางเทคนิคแบบพับเก็บได้ · บทบาทของผู้พัฒนาและช่องทางติดต่อ

ข้อห้าม: ไม่เอ่ยชื่อเทคโนโลยีก่อนถึงหัวข้อภาพรวมทางเทคนิค และไม่อ้างตัวเลขผลลัพธ์ที่ไม่ได้วัดจริง ให้พูดเป็นเจตนาเสมอ

## 13. ภาพรวมทางเทคนิค

Next.js App Router เป็นทั้งส่วนหน้าและส่วนหลัง · PostgreSQL บน Neon · Prisma · deploy บน Vercel
business logic ทั้งหมดอยู่ใน `src/server/<domain>` ที่ไม่ผูกกับ framework ดู [ADR 0001](./adr/0001-nextjs-fullstack-with-isolated-domain-layer.md)
Route Handler หนึ่งเส้นรับ lead จากภายนอก พร้อมหน้าจำลองการยิง lead เข้ามาเพื่อใช้สาธิต
แจ้งเตือนในระบบ และอีเมลสรุปงานค้างประจำวันที่ส่งจริง
มี `docker-compose.yml` ที่รันทั้งระบบได้ในเครื่อง เพื่อรองรับการเล่าว่าย้ายไปติดตั้งบนเซิร์ฟเวอร์ของลูกค้าได้
